Mục tiêu bài học

Hiểu cách Frontend và Off-chain phối hợp hoạt động: từ kết nối ví, truy vấn trạng thái game, xây dựng giao dịch, đến polling chờ xác nhận. Làm quen với CBOR và Plutus Data.

1. Luồng hoạt động tổng quan

Trong bài học trước, chúng ta đã xây dựng xong logic on-chain bằng Aiken. Bây giờ, chúng ta sẽ nhìn vào phần còn lại: làm sao từ các thao tác trên giao diện, có thể biến thành một giao dịch trên Cardano. Để thực hiện điều này, Front-end và Off-chain cần phối hợp chặt chẽ.

Có 4 luồng hoạt động chính trong dApp:

Luồng 1: Khởi tạo & Truy vấn quỹ thưởng

Sau khi mở dApp, Frontend yêu cầu Off-chain cung cấp thông tin trạng thái game. Off-chain sẽ truy vấn Blockfrost để lấy về toàn bộ UTxO tại địa chỉ hợp đồng, sau đó lọc tìm Game UTxO và trả về cho Frontend. Cuối cùng, Frontend đọc dữ liệu và hiển thị lên Game Board.

Luồng 2: Kết nối ví

Ngay khi mở dApp, Frontend tự quét và tìm danh sách các ví đã cài trên trình duyệt. Khi người dùng chọn một ví và nhấn kết nối, yêu cầu được gửi đến ví. Nếu là lần đầu tiên, một popup yêu cầu cấp quyền sẽ hiện ra. Sau khi xác nhận, Frontend truy cập thông tin ví (địa chỉ, collateral...) và mở khóa bảng nhập số.

Luồng 3: Gửi giao dịch đoán số

Người chơi nhập số đoán và số bí mật mới, nhấn Submit. Frontend chuyển thông tin cho Off-chain để xây dựng giao dịch. Giao dịch thô được trả về, chuyển sang ví để ký và gửi lên mạng lưới. Mã giao dịch (Transaction Hash) được trả về.

Luồng 4: Transaction Polling (Chờ xác nhận)

Sau khi submit, giao diện hiển thị "Đang chờ xác nhận...". Hệ thống chạy vòng lặp kiểm tra liên tục (mỗi 5 giây, tối đa 150 giây) xem giao dịch đã được ghi nhận trên Blockfrost hay chưa. Nếu thành công → thông báo chiến thắng và cập nhật Game Board. Nếu hết thời gian → thông báo để người chơi kiểm tra trên explorer.

2. Cấu trúc Frontend

Giao diện dApp được xây dựng bằng Next.js và Framer Motion, tích hợp SDK MeshJS để xử lý các tác vụ Web3 trực tiếp trên trình duyệt.

  • queries.ts — Truy xuất dữ liệu game trên blockchain
  • transactions.ts — Tạo giao dịch đoán số

3. Kết nối ví (Connect Wallet)

Để dApp tương tác được với ví Cardano, chúng ta sử dụng class BrowserWallet từ package @meshsdk/wallet.

Lưu ý: Mesh cung cấp sẵn component <CardanoWallet /> trong @meshsdk/react. Tuy nhiên, package này đã lên v2 (beta) với API mới, trong khi @meshsdk/core vẫn ở v1.9.1 ổn định. Do đó, chúng ta tự viết component kết nối ví — qua đó hiểu rõ hơn cơ chế hoạt động bên trong.

Bước 1: Quét danh sách ví đã cài đặt

// WalletConnect.tsx
useEffect(() => {
  const wallets = BrowserWallet.getInstalledWallets();
  setInstalledWallets(wallets as InstalledWallet[]);
}, []);

Hàm getInstalledWallets() quét trình duyệt và trả về danh sách các extension ví hỗ trợ chuẩn CIP-30. Mỗi phần tử chứa: mã id, tên và biểu tượng ví.

Bước 2: Kết nối vào ví người dùng chọn

// WalletConnect.tsx
const handleConnect = async (walletId: string) => {
  ...
  const connectedWallet = await BrowserWallet.enable(walletId);
  onConnect(connectedWallet);
  ...
};

BrowserWallet.enable(walletId) kích hoạt kết nối đến ví. Popup yêu cầu phê duyệt sẽ hiện ra nếu là lần đầu kết nối. Hàm trả về đối tượng BrowserWallet chứa các API được ủy quyền.

Bước 3: Nhận instance ví và lấy thông tin

// page.tsx
const handleWalletConnect = async (connectedWallet: BrowserWallet) => {
  setWallet(connectedWallet);
  
  // Lấy địa chỉ ví → đích đến cho phần thưởng 10 ADA
  const addr = await connectedWallet.getChangeAddress();
  setWalletAddress(addr);
  ...
  // Kiểm tra UTxO thế chấp (collateral) 
  const collateral = await connectedWallet.getCollateral();
  setHasCollateral(collateral && collateral.length > 0);
  ...
};

Khi ví được kết nối thành công, dApp có quyền yêu cầu lấy địa chỉ ví, collateral, ...

4. Truy vấn dữ liệu (Querying)

Trước khi người dùng có thể đoán số, dApp phải tìm được vị trí kho tiền đang nằm ở đâu trên blockchain.

Hàm fetchGameData

Khi người dùng mở trang, hàm fetchGameData sẽ được kích hoạt. Nó gọi đến getGameUtxo trong off-chain để lấy về Game UTxO, rồi cập nhật các trạng thái hiển thị: quỹ thưởng hiện tại, raw datum.

fetchGameData được gọi trong useEffect, chạy lần đầu khi dApp khởi chạy và tự động kích hoạt lại mỗi khi địa chỉ ví thay đổi.

Hàm getGameUtxo (trong queries.ts)

// Lấy tất cả UTxO đang có ở địa chỉ script
const utxos = await provider.fetchAddressUTxOs(scriptAddress);
...
// Lọc UTxO hợp lệ có Datum đúng cấu trúc game
const validGameUtxos = utxos.filter((utxo) => isValidGameDatum(utxo.output.plutusData));
...
// Chọn UTxO có lượng ADA nhiều nhất
const highestAdaUtxo = validGameUtxos.reduce((prev, current) => {
    const prevAda = prev.output.amount.find(a => a.unit === "lovelace")?.quantity || "0";
    const currentAda = current.output.amount.find(a => a.unit === "lovelace")?.quantity || "0";
    return BigInt(prevAda) > BigInt(currentAda) ? prev : current;
});

Quy trình lọc này ngăn chặn lỗi do kẻ tấn công spam UTxO rác vào địa chỉ hợp đồng. Phương án chọn UTxO có ADA cao nhất không đảm bảo 100% lựa chọn đúng Game UTxO chính thức, nhưng đủ an toàn cho yêu cầu hiện tại.

Giải pháp chuẩn: Sử dụng State Thread Token (đính kèm một NFT vào state UTxO để đánh dấu). Chúng ta sẽ tìm hiểu cách này ở các module sau.

Xem cách hàm isValidGameDatum kiểm tra Game Datum ở phần sau.

5. Plutus Data & CBOR

Trước khi xem cách off-chain xử lý datum, hãy tìm hiểu Cardano lưu dữ liệu trên chuỗi như thế nào.

Pipeline chuyển đổi dữ liệu

Ngôn ngữ smart contract thực sự chạy trên Cardano là Plutus Core, tên đầy đủ là Untyped Plutus Core (UPLC). Các validator viết bằng Aiken, hay Opshin, Plinth, Plu-ts ..., cuối cùng đều được biên dịch về Plutus Core. Các dữ liệu mà validator sử dụng cũng vậy. Datum hay Redeemer trước khi gửi lên chuỗi cần phải chuyển đổi sang Plutus Data trước khi gửi lên chuỗi.

Câu hỏi: Giá trị Plutus Data có được mang nguyên lên blockchain Cardano hay không?
Trả lời: Không. Nó sẽ qua thêm 1 bước mã hóa thành định dạng CBOR rồi mới được đưa lên chuỗi. Bước mã hóa này được gọi là serialize.

Ví dụ với kiểu MyDatum:

Giải mã CBOR từng byte

Phân tích chuỗi d8799f190378ff — tổng cộng 7 bytes:

Bytes Ý nghĩa
d879 CBOR tag 121 → Constructor index 0 (constructor đầu tiên trong type Aiken)
9f Bắt đầu indefinite-length array
19 0378 Tag 19: chỉ định 2 byte tiếp theo là số nguyên dương. 0378 = 888 trong hệ thập lục phân
ff Kết thúc array (break code)

CBOR (Concise Binary Object Representation) là định dạng nhị phân có cấu trúc, tương tự JSON dạng nhị phân. Giúp làm gọn dữ liệu, tiết kiệm dung lượng lưu trữ. Toàn bộ transactions, datums, redeemers và scripts đều encode bằng CBOR trước khi ghi lên chain.

Biểu diễn trong MeshJS

Mesh mô phỏng giá trị Plutus Data bằng đối tượng JavaScript:

// MeshJS representation
{
  constructor: 0,
  fields: [{ int: 888 }]
}

Khi xử lý giá trị datum trên chuỗi bằng MeshJS, chúng ta cần chuyển đổi nó về dạng đối tượng Plutus Data như trên. Việc chuyển đổi này có thể được thực hiện bởi hàm deserializeDatum() hoặc parseDatumCbor().

Hàm tiện ích mConStr0

Khi muốn khởi tạo giá trị datum/redeemer trong Mesh, cách đơn giản nhất là dùng hàm mConStr:

mConStr(0, [888n]) // → Plutus Data: Constr(0, [Int(888)])

Hoặc các hàm dẫn xuất: mConStr0, mConStr1, mConStr2, mConStr3 tạo constructor có index tương ứng:

mConStr0([888n])

Khi build giao dịch, MeshTxBuilder có nhiệm vụ serialize các giá trị này và toàn bộ giao dịch sang định dạng CBOR.

Hàm isValidGameDatum (trong queries.ts)

Hàm này kiểm tra UTxO có chứa datum game hợp lệ hay không:

  1. Đảm bảo UTxO có Inline Datum (giá trị raw datum phải có kiểu string và không rỗng).
  2. Sử dụng deserializeDatum để chuyển đổi CBOR thành đối tượng Mesh Plutus Data.
  3. Kiểm tra: constructor index = 0, fields chứa đúng 1 phần tử mang thuộc tính int, giá trị nằm trong khoảng [1, 999.999].

6. Xây dựng giao dịch (Building Transaction)

Khi người chơi nhấn Submit, dữ liệu đi qua GuessForm → handleSubmit (kiểm tra tính hợp lệ) → handleSubmitGuess (component cha).

Kiểm tra trước khi tạo giao dịch

  • Đã kết nối ví ✓
  • Đã có blockchain provider ✓
  • Đã tìm thấy Game UTxO ✓
  • Ví đã thiết lập collateral ✓

Trước khi tạo giao dịch, gọi fetchGameData() lần nữa để đảm bảo lấy được Game UTxO mới nhất — vì hoàn toàn có khả năng một người chơi khác vừa chiến thắng khiến Game UTxO thay đổi.

Hàm buildGuessTransaction (trong transactions.ts)

Khởi tạo giá trị redeemer và game datum mới:

const redeemerData = mConStr0([BigInt(guess)]);
const newDatumData = mConStr0([BigInt(newSecret)]);

Tính toán số lượng ADA trả lại về hợp đồng:

const newScriptLovelace = currentScriptLovelace - REWARD_AMOUNT_LOVELACE;

Tạo giao dịch:

await txBuilder
  .spendingPlutusScriptV3()             // Giao dịch tiêu UTxO từ địa chỉ PlutusV3 script
  .txIn(txHash, outputIndex, ...)       // Khai báo UTxO được chi tiêu
  .txInInlineDatumPresent()             // Sử dụng Inline Datum sẵn trên UTxO
  .txInRedeemerValue(redeemerData)      // Đính kèm Redeemer (số đoán)
  .txInScript(SCRIPT_CBOR)             // Cung cấp bytecode validator để node chạy
  .txOut(SCRIPT_ADDRESS, [...])         // Khai báo Continuing output
  .txOutInlineDatumValue(newDatumData)  // Datum mới đính kèm continuing output
  .changeAddress(userAddress)           // ADA thừa (phần thưởng) về ví người chơi
  .txInCollateral(...)                 // Khai báo collateral
  .complete();                         // Hoàn thiện giao dịch thô

Mỗi method trên trực tiếp phản ánh một yêu cầu của validator on-chain. Xây dựng sai bất kỳ bước nào → validator reject → giao dịch thất bại.

changeAddress(userAddress): Nhờ câu lệnh này, chúng ta không cần tạo một output trực tiếp vào ví người chơi. Khi txBuilder cân bằng giao dịch, sẽ thừa ra 10 ADA. Giá trị này, sau khi trừ phí giao dịch, sẽ được tự động chuyển về change address.

7. Ký, gửi giao dịch & Transaction Polling

Sau khi buildGuessTransaction trả về giao dịch thô:

// Ký giao dịch
const signedTx = await wallet.signTx(unsignedTx);
...
// Gửi lên mạng lưới
const hash = await wallet.submitTx(signedTx);
...
// Polling: kiểm tra xác nhận (mỗi 5 giây, tối đa 150 giây)
setTxStatus("confirming");
let confirmed = false;
for (let i = 0; i < 30; i++) {
  await new Promise((r) => setTimeout(r, 5000));
  try {
    const txInfo = await provider.fetchTxInfo(hash);
    if (txInfo) {
      confirmed = true;
      break;
    }
  } catch {
    // Chưa confirmed, tiếp tục chờ
  }
}

Trong suốt quá trình này, component TransactionStatus ghi nhận sự thay đổi trạng thái giao dịch để hiển thị lên màn hình: Building → Signing → Confirming → Success / Submitted.
